El presupuesto de memoria

Dónde vive cada dato de la red en el ESP32-S3, cómo el planificador hace entrar 235 KiB de tensores en 54 KiB, y cuánto cuesta poner la arena en PSRAM.

al terminar este nivel vas a poder…

  • Ubicar pesos, activaciones y memoria de trabajo en flash, SRAM o PSRAM, y decir por qué.
  • Explicar cómo la arena separa lo que vive una inferencia de lo que vive todo el programa.
  • Seguir al planificador mientras acomoda los tensores del detector y calcular el pico.
  • Estimar si un doble buffer de cámara entra en la SRAM.
  • Interpretar por qué la arena en PSRAM cuesta 15 % y no varias veces más.

El problema: 512 KB para todo

El ESP32-S3 tiene 512 KB de SRAM interna: memoria rápida dentro del chip, que se lee y se escribe en un ciclo. Ahí tienen que entrar el programa que corre desde RAM, las pilas de las tareas, el Wi-Fi si se usa, la imagen de la cámara y la red neuronal.

La red tiene dos clases de datos (Microcontroladores, Tomo 1, nivel 4). Los pesos son constantes: 214 KiB en el detector. Las activaciones son los resultados de cada capa: se escriben y se leen en cada imagen. Si cada capa guardara su salida aparte, el detector necesitaría 235 KiB solo para ellas.

La respuesta corta: los pesos se quedan en la flash y se leen a través de la caché. Las activaciones van a la arena, un bloque fijo donde un planificador reutiliza las direcciones: el detector necesita 54 KiB en el peor momento. Con la arena en SRAM tarda 47 ms; en PSRAM, 54 ms.

La memoria vista desde afuera

Para la red, el micro ofrece tres memorias. La SRAM interna es chica y rápida. La flash es un chip aparte de varios MB que guarda el programa y el modelo; en la práctica solo se lee mientras corre la red. La PSRAM es otro chip opcional de varios MB, más lento que la SRAM, que se lee y se escribe.

La flash y la PSRAM no se leen directo: el núcleo pide una dirección y la caché, una memoria chica dentro del chip, le entrega una copia (Microcontroladores, Tomo 5, nivel 3). Si no la tiene, la trae por el bus MSPI, que la flash y la PSRAM comparten, igual que su reloj.

Adentro: qué es cada dato y dónde conviene

Cada dato de la red tiene un patrón de uso, y el patrón decide su lugar.

  • Pesos y bias: no cambian y se leen en orden, filtro por filtro. Quedan en la flash, dentro del archivo del modelo, porque la caché aprovecha bien una lectura ordenada.
  • Activaciones: cada capa escribe su salida y la capa siguiente la lee. Viven poco: desde que se calculan hasta que las usa el último que las necesita.
  • Memoria de trabajo de los kernels: algunos kernels de ESP-NN piden un espacio temporal, por ejemplo para reordenar datos antes de multiplicar. Vive lo que dura la capa.
  • Datos del intérprete: la descripción de cada tensor (forma, escala, dirección) se arma al preparar y vive todo el programa.

Los tres últimos van a la arena. La arena es un solo bloque de bytes que el programa reserva al arrancar. Así no se pide memoria suelta durante la inferencia, que podría fallar por fragmentación o tardar distinto cada vez.

LiteRT Micro organiza la arena como dos pilas que crecen una hacia la otra. La cabeza, desde abajo, guarda lo que vive una inferencia: activaciones y memoria de trabajo. La cola, desde arriba, guarda lo que vive todo el programa. Si al preparar se tocan, la arena es chica y el programa avisa.

analogía: la mesa del taller

La cola es la morsa atornillada a la mesa: está siempre en el mismo lugar. La cabeza es el espacio libre de la mesa, donde apoyás la pieza que estás haciendo y, cuando la terminás, ponés la siguiente en el mismo lugar.

Recorrido: el planificador acomoda el detector

Antes de la primera inferencia, el planificador decide la dirección de cada activación dentro de la cabeza. Conoce dos datos de cada tensor: su tamaño en bytes y su vida, el rango de nodos del grafo durante el que tiene que conservarse.

  1. Listar los tensores. El detector tiene 32 tensores de activación. Por ejemplo, la salida de la primera capa 1×1 mide 48×48×16 = 36 864 bytes y vive desde el nodo 2, que la escribe, hasta el nodo 3, que la lee.
  2. Ordenar de mayor a menor. Los tensores grandes son los más difíciles de ubicar, así que van primero. Es la regla first-fit decreasing que describen los autores de LiteRT Micro.
  3. Ubicar cada uno en el primer hueco. Para cada tensor, el planificador prueba desde la dirección 0 y sube hasta encontrar un hueco donde no pise a ningún tensor que viva al mismo tiempo. Los que no conviven pueden usar las mismas direcciones.
  4. Medir el pico. La dirección más alta ocupada es el tamaño que necesita la cabeza. En el detector son 55 296 bytes: la salida de 36 KiB de esa capa 1×1 más su entrada de 18 KiB.

El ejemplo de Espressif reserva 100 KiB para la cabeza y la cola, y 60 KiB más de memoria de trabajo para ESP-NN: 160 KiB en total. Los 54 KiB de activaciones entran con margen; el resto se reparte entre la cola y los huecos que deja el planificador.

Cómo se encadena: la imagen y la caché

La arena no es lo único que necesita SRAM. La cámara escribe cada cuadro por DMA en un buffer, y con un doble buffer hay dos: la cámara llena uno mientras la red procesa el otro (nivel 5). Con imágenes de 96×96 en gris son 18 KiB, pero con QVGA en color son 300 KiB.

Si la arena se muda a la PSRAM, cada activación pasa por la caché. Sin embargo, Espressif mide apenas 7 ms más en el detector. Una explicación probable: el pico de activaciones, 54 KiB, cabe en la caché de datos del S3, configurable hasta 64 KB, y casi todo se lee y se escribe sin salir del chip (por confirmar).

ojo: el 15 % vale para este detector

Una red con activaciones más grandes que la caché sí sufre con la arena en PSRAM: cada fallo trae una línea por el bus que también usa la flash. La cifra de 15 % no se puede llevar a otra red sin medir.

En un Cortex-M las memorias TCM (tightly coupled) cumplen el papel de la SRAM interna del S3: responden en un ciclo y no pasan por la caché. Con una NPU Ethos-U, el compilador Vela decide de antemano qué tensores van a la SRAM y cuáles a la memoria externa, y la NPU los mueve sola.

dato: estándares

  • AXI y AHB son buses de la familia AMBA de Arm; la NPU Ethos-U se conecta por AXI para leer pesos y activaciones sin la CPU.
  • La PSRAM del S3 sigue la interfaz Octal SPI con doble flanco (DDR): 8 líneas de datos que transfieren en los dos flancos del reloj.

Relación con el resto del micro

La flash se ve en el mapa de memoria gracias a la MMU, que traduce direcciones de 64 KB en 64 KB (Microcontroladores, Tomo 5, nivel 1). El DMA de la cámara escribe en SRAM o PSRAM sin la CPU (Microcontroladores, Tomo 3, nivel 4). Los kernels que usan la arena son los del nivel 3.

cálculo: el pico de activaciones

P = máx (entradak + salidak)

entrada
48·48·8 = 18 432 bytes (salida de la capa anterior)
salida
48·48·16 = 36 864 bytes (primera capa 1×1)
sin reutilizar
241 030 bytes: la suma de los 32 tensores

P = 18 432 + 36 864 = 55 296 bytes ≈ 54 KiB; 241 030 / 55 296 ≈ 4,4 veces menos

En una red en cadena, el pico lo fija la capa con más entrada más salida, no la red entera. Las cuentas salen de la arquitectura publicada.

Con la arena de 160 KiB, el doble buffer QVGA llevaría la SRAM al 90 % sin contar programa ni Wi-Fi: en color, los cuadros van a la PSRAM.

cálculo: SRAM contra PSRAM

BW = bytes por transferencia · transferencias por segundo

SRAM
16 bytes por ciclo a 240 MHz (supuesto: una carga del PIE por ciclo)
PSRAM
1 byte por flanco, 2 flancos por ciclo, a 80 MHz (Octal DDR, sin contar comandos)

SRAM: 16 · 240 · 10⁶ = 3,84 GB/s; PSRAM: 2 · 80 · 10⁶ = 160 MB/s; cociente ≈ 24

La PSRAM es del orden de 24 veces más lenta en el mejor caso. Que el detector pierda solo 15 % muestra cuánto trabajo hace la caché.

Límites y datos por confirmar

El planificador real de LiteRT Micro tiene más detalles que el de este nivel, como alinear cada tensor a 16 bytes. Las cuentas del detector salen de su arquitectura, no del archivo. Quedan por confirmar estos puntos:

  • que el pico entre en la caché de datos sea la causa de la pérdida chica en PSRAM;
  • cuánta SRAM queda libre con Wi-Fi activo en una configuración concreta de ESP-IDF;
  • cuánto de los 60 KiB de trabajo usa realmente cada kernel del detector;
  • la cifra de "varias veces más lenta" con PSRAM que circula en algunos textos, incluido el Tomo 1: para este detector Espressif mide 15 %.

para llevar

  • Pesos en la flash, leídos por la caché; activaciones, memoria de trabajo y datos del intérprete en la arena.
  • La arena tiene dos pilas: la cabeza para lo que vive una inferencia y la cola para lo que vive todo el programa.
  • El planificador ordena los tensores de mayor a menor y los ubica en el primer hueco: el detector pasa de 235 KiB a 54 KiB.
  • Un doble buffer en color no entra en la SRAM del S3; en gris ocupa 18 KiB.
  • La arena en PSRAM cuesta 15 % en el detector porque la caché absorbe casi todo; en otra red hay que medir.

firmware · el planificador en C

Este código sigue el recorrido: ordena los tensores de mayor a menor y sube a cada uno hasta un hueco donde no pise a otro que viva al mismo tiempo. Devuelve el pico, el tamaño que necesita la cabeza.

Con los ocho tensores de la figura 2.2 da las mismas direcciones y un pico de 55 296 bytes.

ver el código 
/* Planificador "first-fit decreasing", como el que describe
   el artículo de LiteRT Micro: ordenar los tensores de mayor
   a menor y poner cada uno en la dirección más baja que no
   choque con otro vivo al mismo tiempo. */
#define MAX_T 64

typedef struct {
    int tam;      /* bytes                         */
    int nace;     /* primer nodo que lo usa        */
    int muere;    /* último nodo que lo usa        */
    int dir;      /* resultado: dirección en arena */
} Tensor;

/* ¿Comparten algún nodo? Si no, pueden pisarse. */
static int vivos_juntos(const Tensor *a, const Tensor *b)
{
    return !(a->muere < b->nace || b->muere < a->nace);
}

/* Devuelve el pico: los bytes que necesita la arena. */
int planificar(Tensor *t, int n)
{
    int orden[MAX_T], pico = 0;
    for (int i = 0; i < n; i++)
        orden[i] = i;
    /* Ordenar de mayor a menor (inserción). */
    for (int i = 1; i < n; i++)
        for (int j = i; j > 0 &&
             t[orden[j]].tam > t[orden[j-1]].tam; j--) {
            int x = orden[j];
            orden[j] = orden[j-1];
            orden[j-1] = x;
        }
    for (int k = 0; k < n; k++) {
        Tensor *a = &t[orden[k]];
        int dir = 0, movido = 1;
        /* Subir mientras pise a un tensor vivo. */
        while (movido) {
            movido = 0;
            for (int m = 0; m < k; m++) {
                Tensor *b = &t[orden[m]];
                int pisa = dir < b->dir + b->tam &&
                           b->dir < dir + a->tam;
                if (vivos_juntos(a, b) && pisa) {
                    dir = b->dir + b->tam;
                    movido = 1;
                }
            }
        }
        a->dir = dir;
        if (dir + a->tam > pico)
            pico = dir + a->tam;
    }
    return pico;
}
